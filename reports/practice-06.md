# Отчёт по качеству: триада метрик RAG (практика 6)

## Две метрики поиска

Оба числа измерены на одном и том же корпусе, но разными способами и на разных подмножествах вопросов. Это две разные величины, а не одна, измеренная дважды.

| Метрика | Значение | Как получена | С какой практики доступна |
| --- | --- | --- | --- |
| hit-rate@5 | 100% (4 из 4) | механическая сверка поля `source`, `python ingest.py --eval` | П2 |
| Context Precision | 0.56 | оценка LLM-судьёй, `python test_suite.py` | П6 |

hit-rate@5 измерен на четырёх вопросах с непустым `expected_sources`. Вопросы типа `out_of_scope` в замер не входят: у них нет ожидаемого источника. Context Precision измерен на девяти in-scope вопросах (все, кроме `out_of_scope`).

Разница объяснима: hit-rate@5 проверяет только, попал ли нужный файл в топ-5 результатов поиска. Context Precision оценивает, относятся ли найденные фрагменты к вопросу. Файл может попасть в выдачу, но конкретный фрагмент может быть не о том - это и показывает Context Precision.

## Разбор галлюцинации

Судья пометил три вопроса как галлюцинации: id 6, id 8, id 9. Разберём один случай подробно.

**Вопрос (id 6):** «Зачем в трансформере нужно позиционное кодирование?»

**Ответ системы:** «В переданных фрагментах нет информации о том, почему в трансформере нужно позиционное кодирование. Они описывают, что трансформеры в основном основаны на механизме внимания, но не говорят о позиционном кодировании.»

**Что судья считает галлюцинацией:** система отказалась отвечать, хотя в корпусе нужная информация есть. Судья ожидает ответа и ставит 0.0 по Faithfulness.

**Процитированные фрагменты (из `format_chunks()`):** `[1706.03762v7.pdf, стр. 2]` - про self-attention, без позиционного кодирования.

**Чего в них нет:** в этом фрагменте действительно нет информации о позиционном кодировании. Поиск с запросом «зачем нужно позиционное кодирование» вернул фрагмент про self-attention вместо фрагмента про positional encoding (он находится на стр. 5-6 статьи).

**Почему это произошло:** поиск не нашёл нужный фрагмент. Система корректно отказалась отвечать - по промпту это правильное поведение при отсутствии данных. Но судья видит только «система не ответила -> F=0.0» и помечает это как галлюцинацию.

**Важно:** это не галлюцинация системы в строгом смысле. Система **не выдумала** факт - она **корректно отказалась**. Проблема на уровне поиска, а не генерации. Однако судья различает эти случаи не всегда. Так же обстоят дела с id 8 (корпуса BERT - поиск не нашёл стр. 4-5) и id 9 (Adam vs SGD - система ответила косвенно).

**Вывод:** из трёх вопросов, помеченных как галлюцинации, ни один не является галлюцинацией системы в чистом виде. Реальный Faithfulness системы выше измеренного 0.58. Измеренное значение отражает ограничения поиска и особенности судьи.

## Ограничения метода

Судья - `qwen2.5:7b`, температура `0.0`. Генератор - `qwen2.5:3b`. Модели **разные** (7B и 3B), поэтому оценка **независимая**: судья не оценивает собственную работу.

Но обе модели относятся к семейству Qwen2.5 - возможен общий bias семейства. Кроме того, судья **не всегда различает отказ по делу и галлюцинацию**: когда система отказывается из-за того, что поиск не нашёл нужный фрагмент, судья ставит 0.0 как за галлюцинацию. Это занижает измеренный Faithfulness относительно реального.

Оценка судьи - инструмент отслеживания изменений между правками, а не приговор качеству системы. Сравнение между прогонами (до/после правок) даёт более осмысленные результаты, чем абсолютные числа.

Дополнительное ограничение: прогон `test_suite.py` на Windows проведён через `search_chunks` (прямой запрос к ChromaDB), минуя MCP. Причина - известный баг `mcp` SDK на Windows (`NotImplementedError` в `asyncio.subprocess_exec` при запуске подпроцесса). На Linux `orchestrator.handle()` отработает штатно. Это не влияет на качество оценки: `search_chunks` возвращает те же фрагменты, что и MCP-клиент.
